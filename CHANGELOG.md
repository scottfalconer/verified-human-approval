# Changelog

Newest first. Until 1.0, a minor version may change interfaces; [docs/releasing.md](docs/releasing.md) says what each version promises.

## Unreleased: 0.1.0

The first release, of seven packages: `verified-human-approval/core`, `webauthn`, `mcp`, `symfony-bundle`, `doctrine`, `store-contracts` and `testing`. They need PHP 8.3 or later, and the bundle Symfony 7.4 or 8. [Architecture and request lifecycle](docs/overview.md) shows how they fit together.

### Approvals

- **Approval of an exact action.** Where its rule requires approval, the application freezes the exact proposal as canonical JSON with its SHA-256 digest. Only a passkey assertion bound to that digest approves it, and only the person who asked can approve. A caller without permission is refused, and an action the rule lets run directly runs at once and is recorded as `not_required`.
- **One execution, in one transaction.** On approval, the application rechecks current permissions, the rule and the action's preconditions, then runs the stored proposal once. The action's writes on the application's database connection, the proof, the execution record and, with a receipt signer, the receipt signed with the application's key commit together, or none do. If the application's trusted keys do not cover its signer at that moment, the action rolls back instead. This holds while the action leaves the transaction to the store: one that commits, rolls back or replaces it itself gets no outcome recorded, since the supplied approval stores refuse every write once the transaction has ended.
- **After it runs.** The running action can read which approval it runs under (`ExecutionGuard::current()`). After the commit, `ApprovalObserver` services are told and the bundle dispatches `ApprovalCompleted`, best effort and possibly more than once.
- **Records checked as they are read.** Before `ApprovalService` reports, replays, offers or changes a stored request, it checks that the stored parts agree and, with a receipt signer, that the receipt signed at commit still verifies. A record that fails, or cannot be read back, is `record_integrity_error`, which `ApprovalFlow::errorResult()` reports as `integrity_error`, never as a refusal; history and audit lists put an `UnreadableApproval` in its place. For such a record, the bundle's review page says that the outcome cannot be confirmed (HTTP 409), and a page of your own can render the same `@VerifiedHumanApproval/integrity_error.html.twig`, with the request's id or without it. A stored passkey ceremony that does not read back is refused as `corrupt_ceremony`, and the person starts a fresh review. See [Protection after storage](docs/security-model.md#protection-after-storage).

### Receipts, audit log and passkeys

- **Receipts.** With a receipt signer, the application signs each action's proposal, proof and execution record (their digests) with Ed25519 as the action commits. `verify-evidence.php` checks the receipt offline against the application's trusted keys, so it still checks after a key rotation. When the check fails, it says what did not match, such as a record that is not what the application signed, with the part that changed, or a receipt the trusted key did not sign. For some evidence it cannot read, such as a proposal that no longer reads back as a proposal, it says only that the evidence does not verify. With the bundle, the person downloads it from the review page, the agent's result carries it, and `/approval/receipt-keys.json` publishes the keys. See [Verify a receipt](docs/evidence.md).
- **A signed audit log** of security events, such as passkey enrollments and revocations: one hash chain of signed entries, a head to keep elsewhere as a checkpoint (`verified-human-approval:audit-head`), and key rotations recorded in the chain (`verified-human-approval:record-key-rotation`), so what an old key signed stays checkable. An `AuditLog` remembers up to 50,000 signatures that verified and does not check them again. A reading of the log still holds all of it in memory, so give PHP more than its default 128M `memory_limit` well before the log reaches 23,000 entries ([Protection after storage](docs/security-model.md#protection-after-storage) gives the figures). See [Keep checkpoints of the audit log](docs/evidence.md#keep-checkpoints-of-the-audit-log).
- **Passkeys through WebAuthn** (`web-auth/webauthn-lib`), with user verification required. The refusal of a passkey response or a stored passkey keeps, as its previous exception, the class of what failed inside the library and the line of the check that raised it, never its message or the data it carried. See [the WebAuthn package](src/webauthn/README.md).
- **Trusted enrollment.** When the verifier reads passkeys through `AnchoredCredentialRepository`, as it does with `persistence: { driver: doctrine }`, in the [worked example](src/symfony-bundle/docs/first-action.md#2-configure-keys-and-services) and in the demo, a passkey approves only while a signed enrollment entry in the audit log vouches for it, so a row inserted in the database, or given another public key there, approves nothing. Each approval step weighs all of the person's passkeys from one reading of the log. Any trace of a passkey's revocation in the log stops it for good. An entry since its enrollment that the log refuses, for its signature, key, window, link or rotation, stops it until the log accepts that entry, which it never does for one signed after the rotation away from its key. A person left with only such passkeys is told to ask the site's administrator (`credential_unvouched`). They can enroll another passkey, but since the stopped ones cannot confirm it, that takes an authorization that does not rest on them, such as a one-time link. A plain credential repository gives no such protection. See [Trusted enrollment](src/webauthn/README.md#trusted-enrollment).

### MCP

- **The approval card**, an MCP App beside a protected tool's result. It opens the review page, follows the request through the status tool and can offer a one-time phone code; it never runs the passkey ceremony. It opens pages only on the origin it was written for and calls only the tools written into it. See [The card](src/mcp/README.md#the-card).
- **Card colors.** The card paints its own surface and sets `color-scheme` from the host's theme, so a color the host sends as `light-dark()` takes that theme's side. It uses the host's colors only as a pair, the host's text on the host's surface, and only where that text is readable in that theme; otherwise it uses its own. Until the host answers or 300 ms pass, it paints no surface, so a device set to light does not flash a white card inside a dark app. No check of the card in the Claude iOS app is recorded. `tests/card_smoke.py` checks the colors under dark, light and mismatched hosts and under hosts that send no styles.
- **Request keys.** `ApprovalFlow::REQUEST_KEY_DESCRIPTION` describes a tool's optional request key so that a language model leaves it out. Asked for one in the demo, Claude models built it from the alert's id, its revision and sometimes the date, and often built the same key again in a later conversation, which returns the earlier request's outcome. When a key names a request that finished earlier, the result says that nothing ran for this call. `tests/claude_request_key.py` checks the description against Claude models. See [The request key argument](src/mcp/README.md#the-request-key-argument).
- **A budget for agent requests.** Each call that may open a proposal spends one from the person's `ProposalBudget`, as the MCP tools specification asks; reading an outcome is free. In the bundle it is a rate limiter per person, set by `agent_requests_per_minute` (30 by default). See [Rate limiting](src/mcp/README.md#rate-limiting).
- **URL-mode elicitation**, optional, for the clients the application lists, on MCP 2026-07-28 or later. Its retry is bound to the caller, the tool and the arguments, and only reads the stored outcome. See [The URL-mode elicitation and its retry](src/mcp/README.md#the-url-mode-elicitation-and-its-retry).

### Symfony bundle

- **Review pages** on the application's own origin, with CSRF checks, a rate limit on approval attempts, a strict Content-Security-Policy with a nonce for your layout, and the `VerifiedHumanApproval` translation domain. After approval they point the person back to the page the request came from, or to the agent that asked. See [Your layout and language](src/symfony-bundle/docs/index.md#your-layout-and-language).
- **Expired sign-ins.** The page's script recognizes the host's `401` with `{"status":"authentication_required"}` and links back to the same request to sign in, without claiming an outcome it could not confirm. See [Recover an expired browser session](src/symfony-bundle/docs/authentication.md#recover-an-expired-browser-session).
- **A "verified" badge**, shown only for a passkey approval, while the page shows exactly the approved values and the receipt still verifies, with an optional public page it links to. See [Show that a change was approved](src/symfony-bundle/docs/index.md#show-that-a-change-was-approved).
- **The phone code.** On HTTPS, `approval_handoff` gives the card a QR code that opens one pending review on the person's phone, once and within two minutes, and still needs the passkey. `phone_handoff: false` turns it off. See [Register the MCP tools and card](src/symfony-bundle/docs/index.md#4-register-the-mcp-tools-and-card).
- **Scope challenges for MCP over HTTP**, opt-in: `McpScopeChallengeSubscriber` applies the SDK's `ScopePolicy` and answers a token that lacks a tool's scope with HTTP 403, `insufficient_scope` and every scope the operation needs. See [Scope challenges over HTTP](src/symfony-bundle/docs/index.md#scope-challenges-over-http).
- **Configuration that cannot work does not build**: `public_verification`, `persistence` or `receipt_keys` without a `receipt_signer`; a URL prompt for no client; a Content-Security-Policy source such as `'unsafe-inline'`; an MCP server that lists the phone tool while `phone_handoff` is off, or that serves the approval card without it while `phone_handoff` is on; `McpScopeChallengeSubscriber` with no MCP server over HTTP.

### Storage

- **SQLite through PDO.** `PdoApprovalStore`, `PdoAuditStore` and `PdoCredentialRepository` keep approvals, the audit log and passkeys on the application's own connection, and the audit store and the application's own writes join the approval's transaction. They change none of the connection's settings, such as its busy timeout or foreign keys, and refuse a connection that does not throw on errors.
- **Doctrine** (`verified-human-approval/doctrine`): the same three stores on the application's DBAL connection, on SQLite, PostgreSQL, MySQL 8.0.17+ and MariaDB, in one transaction with its entities. With the ORM: a base action that locks and flushes inside the approval, a flush check that refuses unapproved changes to protected entities and fields (`#[RequiresApproval]`, embedded objects included) and a schema listener for migrations. The bundle wires it with `persistence: { driver: doctrine }`. See [the Doctrine package](src/doctrine/README.md).
- **Storage contracts** (`verified-human-approval/store-contracts`): the PHPUnit suites that an approval store, audit store or passkey repository of your own must pass, with real process races, fault injection and actions that end the approval transaction themselves. When a test ends, the contract calls `close()` on each harness the test connected, before the store is dropped, so a harness can close its connection and a long run stays within the database server's connection limit. See [the storage contracts](src/store-contracts/README.md).

### Testing

- **Testing support** (`verified-human-approval/testing`): a software passkey with real signatures, a BrowserKit driver for the passkey panel and a PSR-18 client that runs an MCP client against your kernel in process. See [Test your application's integration](src/symfony-bundle/docs/testing.md).
- **Checked from outside.** CI installs the packages into separate Composer projects and into [Editorial Desk](tests/EditorialDesk/README.md), an independent Symfony publishing application, MIT licensed like the rest of the repository, and runs its PHP, HTTP and browser checks, including approval records damaged in its database.

### Demo and examples

- **The Riverside Council demo**: an agent asks to issue an alert, and the editor approves the exact public page with a passkey. Its OAuth runs on `league/oauth2-server-bundle` and `omouren/mcp-oauth-bundle`, with its own consent step bound to the exact authorization request, and accepts client ID metadata documents from `claude.ai`, `chatgpt.com`, `vscode.dev` and `cursor.com`. On the consent page, Don't allow sends the person back with `access_denied`, the request's `state` and `iss` (RFC 6749 §4.1.2.1, RFC 9207), but only to a client that a trusted metadata document names or that returns to this computer. A person who refuses a client that registered itself and returns to another computer stays on the demo's own page, and that client's scope errors are not redirected either (RFC 9700 §4.11.2). See [the demo](demo/README.md) and [Authentication ownership](demo/authentication.md).
- **Demo scripts** (macOS): `demo/bin/server` runs the local demo under launchd, at the address it was set up for, and `demo/bin/public` runs a second demo behind a Cloudflare quick tunnel, for claude.ai and phones. Both act only on this checkout's own server and tunnel: a program already on the port, or another checkout's job, is named and left alone. `demo/bin/public start` and `reset` refuse while anything else holds port 8081, which the tunnel publishes, and when either is refused, fails or is interrupted before the public demo is served, this checkout's tunnel stops too. `reset` keeps the demo's address, so once this checkout's tunnel has stopped or come back at a new address, it refuses and says to run `start`. See [public access and phone approval](demo/README.md#optional-public-access-and-phone-approval).
- **Example clients**: `examples/mcp.php` with the PHP MCP SDK's client, and `examples/agent.php` with Symfony AI's `Agent` and `McpToolbox`, which `--scripted` runs without a model API key. `agent.php` prints the review link from the application's tool result on a line of its own, whatever the model replied. See [the examples](examples/README.md).
- **Publishing example** (`examples/doctrine-publishing`): a newsroom on Doctrine ORM where publishing, editing live content, archiving (also a batch, under one approval) and deleting each wait for the editor's passkey, from the browser and from an agent alike. Its tests cover SQLite, PostgreSQL, MySQL and MariaDB. See [Approved publishing on Doctrine](examples/doctrine-publishing/README.md).

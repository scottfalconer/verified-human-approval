# Changelog

Newest first. Until 1.0, a minor version may change interfaces; [docs/releasing.md](docs/releasing.md) says what each version promises.

## Unreleased: 0.1.0

The first release, of seven packages: `verified-human-approval/core`, `webauthn`, `mcp`, `symfony-bundle`, `doctrine`, `store-contracts` and `testing`. They need PHP 8.3 or later, and the bundle Symfony 7.4 or 8. [Architecture and request lifecycle](docs/overview.md) shows how they fit together.

### Approvals

- **Approval of an exact action.** Where its rule requires approval, the application freezes the exact proposal as canonical JSON with its SHA-256 digest. Only a passkey assertion bound to that digest approves it, and only the person who asked can approve. A caller without permission is refused, and an action the rule lets run directly runs at once and is recorded as `not_required`.
- **One execution, in one transaction.** On approval, the application rechecks current permissions, the rule and the action's preconditions, then runs the stored proposal once. The action's writes on the application's database connection, the proof, the execution record and, with a receipt signer, the receipt signed with the application's key commit together, or none do. If the application's trusted keys do not cover its signer at that moment, the action rolls back instead.
- **After it runs.** The running action can read which approval it runs under (`ExecutionGuard::current()`). After the commit, `ApprovalObserver` services are told and the bundle dispatches `ApprovalCompleted`, best effort and possibly more than once.
- **Records checked as they are read.** Before `ApprovalService` reports, replays, offers or changes a stored request, it checks that the stored parts agree and, with a receipt signer, that the receipt signed at commit still verifies. A record that fails, or cannot be read back, is `record_integrity_error`, which `ApprovalFlow::errorResult()` reports as `integrity_error`, never as a refusal; history and audit lists put an `UnreadableApproval` in its place. See [Protection after storage](docs/security-model.md#protection-after-storage).

### Receipts, audit log and passkeys

- **Receipts.** With a receipt signer, the application signs each action's proposal, proof and execution record (their digests) with Ed25519 as the action commits. `verify-evidence.php` checks the receipt offline against the application's trusted keys, so it still checks after a key rotation. With the bundle, the person downloads it from the review page, the agent's result carries it, and `/approval/receipt-keys.json` publishes the keys. See [Verify a receipt](docs/evidence.md).
- **A signed audit log** of security events, such as passkey enrollments and revocations: one hash chain of signed entries, a head to keep elsewhere as a checkpoint (`verified-human-approval:audit-head`), and key rotations recorded in the chain (`verified-human-approval:record-key-rotation`), so what an old key signed stays checkable. See [Keep checkpoints of the audit log](docs/evidence.md#keep-checkpoints-of-the-audit-log).
- **Passkeys through WebAuthn** (`web-auth/webauthn-lib`), with user verification required. When the verifier reads passkeys through `AnchoredCredentialRepository`, as it does with `persistence: { driver: doctrine }`, in the [worked example](src/symfony-bundle/docs/first-action.md#2-configure-keys-and-services) and in the demo, a passkey approves only while a signed enrollment entry in the audit log vouches for it, so a row inserted in the database, or given another public key there, approves nothing. Any trace of its revocation in the log stops it for good, and so does a later entry that the log refuses for its signature, key, window, link or rotation: its owner then enrolls again. A plain credential repository gives no such protection. See [Trusted enrollment](src/webauthn/README.md#trusted-enrollment).

### MCP

- **The approval card**, an MCP App beside a protected tool's result. It opens the review page, follows the request through the status tool and can offer a one-time phone code; it never runs the passkey ceremony. It opens pages only on the origin it was written for and calls only the tools written into it. See [The card](src/mcp/README.md#the-card).
- **Card colors.** The card paints its own surface and sets `color-scheme` from the host's theme, so a color the host sends as `light-dark()` takes that theme's side. It uses the host's colors only as a pair, the host's text on the host's surface, and only where that text is readable in that theme; otherwise it uses its own. Until the host answers or 300 ms pass, it paints no surface, so a device set to light does not flash a white card inside a dark app. In the Claude iOS app on 18 November 2026, a card with a transparent background and no `color-scheme` showed the light theme's dark text over the app's dark surface; no check of this card in that app is recorded. `tests/card_smoke.py` checks the colors under dark, light and mismatched hosts and under hosts that send no styles.
- **Request keys.** `ApprovalFlow::REQUEST_KEY_DESCRIPTION` describes a tool's optional request key so that a language model leaves it out. Asked for one, Claude models built it from the arguments and the date, and often built the same key again in a later conversation, which returns the earlier request's outcome. When a key names a request that finished earlier, the result says that nothing ran for this call. `tests/claude_request_key.py` checks the description against Claude models. See [The request key argument](src/mcp/README.md#the-request-key-argument).
- **A budget for agent requests.** Each call that may open a proposal spends one from the person's `ProposalBudget`, as the MCP tools specification asks; reading an outcome is free. In the bundle it is a rate limiter per person, set by `agent_requests_per_minute` (30 by default). See [Rate limiting](src/mcp/README.md#rate-limiting).
- **URL-mode elicitation**, optional, for the clients the application lists, on MCP 2026-07-28 or later. Its retry is bound to the caller, the tool and the arguments, and only reads the stored outcome. See [The URL-mode elicitation and its retry](src/mcp/README.md#the-url-mode-elicitation-and-its-retry).

### Symfony bundle

- **Review pages** on the application's own origin, with CSRF checks, a rate limit on approval attempts, a strict Content-Security-Policy with a nonce for your layout, and the `VerifiedHumanApproval` translation domain. After approval they point the person back to the page the request came from, or to the agent that asked. See [Your layout and language](src/symfony-bundle/docs/index.md#your-layout-and-language).
- **Expired sign-ins.** The page's script recognizes the host's `401` with `{"status":"authentication_required"}` and links back to the same request to sign in, without claiming an outcome it could not confirm. See [Recover an expired browser session](src/symfony-bundle/docs/authentication.md#recover-an-expired-browser-session).
- **A "verified" badge**, shown only for a passkey approval, while the page shows exactly the approved values and the receipt still verifies, with an optional public page it links to. See [Show that a change was approved](src/symfony-bundle/docs/index.md#show-that-a-change-was-approved).
- **The phone code.** On HTTPS, `approval_handoff` gives the card a QR code that opens one pending review on the person's phone, once and within two minutes, and still needs the passkey. `phone_handoff: false` turns it off. See [Register the MCP tools and card](src/symfony-bundle/docs/index.md#4-register-the-mcp-tools-and-card).
- **Scope challenges for MCP over HTTP**, opt-in: `McpScopeChallengeSubscriber` applies the SDK's `ScopePolicy` and answers a token that lacks a tool's scope with HTTP 403, `insufficient_scope` and every scope the operation needs. See [Scope challenges over HTTP](src/symfony-bundle/docs/index.md#scope-challenges-over-http).
- **Configuration that cannot work does not build**: `public_verification`, `persistence` or `receipt_keys` without a `receipt_signer`; a URL prompt for no client; a Content-Security-Policy source such as `'unsafe-inline'`; an MCP server that lists the phone tool while `phone_handoff` is off; `McpScopeChallengeSubscriber` with no MCP server over HTTP.

### Storage

- **SQLite through PDO.** `PdoApprovalStore`, `PdoAuditStore` and `PdoCredentialRepository` keep approvals, the audit log and passkeys on the application's own connection, and the audit store and the application's own writes join the approval's transaction.
- **Doctrine** (`verified-human-approval/doctrine`): the same three stores on the application's DBAL connection, on SQLite, PostgreSQL, MySQL 8.0.17+ and MariaDB, in one transaction with its entities. With the ORM: a base action that locks and flushes inside the approval, a flush check that refuses unapproved changes to protected entities and fields (`#[RequiresApproval]`, embedded objects included) and a schema listener for migrations. The bundle wires it with `persistence: { driver: doctrine }`. See [the Doctrine package](src/doctrine/README.md).
- **Storage contracts** (`verified-human-approval/store-contracts`): the PHPUnit suites that an approval store, audit store or passkey repository of your own must pass, with real process races and fault injection. See [the storage contracts](src/store-contracts/README.md).

### Testing

- **Testing support** (`verified-human-approval/testing`): a software passkey with real signatures, a BrowserKit driver for the passkey panel and a PSR-18 client that runs an MCP client against your kernel in process. See [Test your application's integration](src/symfony-bundle/docs/testing.md).
- **Checked from outside.** CI installs the packages into separate Composer projects and into [Editorial Desk](tests/EditorialDesk/README.md), an independent Symfony publishing application, MIT licensed like the rest of the repository, and runs its PHP, HTTP and browser checks.

### Demo and examples

- **The Riverside Council demo**: an agent asks to issue an alert, and the editor approves the exact public page with a passkey. Its OAuth runs on `league/oauth2-server-bundle` and `omouren/mcp-oauth-bundle`, with its own consent step bound to the exact authorization request, and accepts client ID metadata documents from `claude.ai`, `chatgpt.com`, `vscode.dev` and `cursor.com`. See [the demo](demo/README.md) and [Authentication ownership](demo/authentication.md).
- **Example clients**: `examples/mcp.php` with the PHP MCP SDK's client, and `examples/agent.php` with Symfony AI's `Agent` and `McpToolbox`, which `--scripted` runs without a model API key. See [the examples](examples/README.md).
- **Publishing example** (`examples/doctrine-publishing`): a newsroom on Doctrine ORM where publishing, editing live content, archiving (also a batch, under one approval) and deleting each wait for the editor's passkey, from the browser and from an agent alike. Its tests cover SQLite, PostgreSQL, MySQL and MariaDB. See [Approved publishing on Doctrine](examples/doctrine-publishing/README.md).

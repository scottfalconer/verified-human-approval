# Security model

Verified Human Approval protects a registered application action. The application freezes the proposed effect, obtains any required passkey approval, checks current authority and commits the effect with its execution record in one transaction.

One proposal can commit the protected effect at most once **within that transaction boundary**. The host application must put every route to that effect through the guarded mutation service.

## What the host must trust

The application code, action adapter, authorization provider, review page, credential enrollment process and evidence signing key are trusted components. The agent is an ordinary client with delegated access. Tool arguments do not select the authenticated user, add a passkey, change an approval rule or provide approval.

`ExecutionGuard` gives the protected mutation service a capability to run only the exact prepared action for the exact actor. Approval and ordinary authorization are both required checks. Configure every supported route, CLI command and job to use that boundary. The optional Doctrine protected-entity listener also rejects unapproved unit-of-work writes to protected entities and fields. It does not catch DQL bulk updates and deletes or raw SQL. Inside an embedded object (`#[ORM\Embedded]`), `#[RequiresApproval]` on the embedded property protects each of its fields, and the attribute on a property of the embeddable class protects that field or embedded object wherever the embeddable is used; the configuration names them as Doctrine does, such as `published` or `published.title`. Writes it does not catch must stay behind the guarded service.

This is an application boundary, not a sandbox. Whoever can change the application's code, write directly to its database or read its signing key is inside the boundary, and so is an agent given that access, such as a coding agent that can edit the running application's files or database. An agent the approval is meant to hold back must reach the application only through its tools.

## Transaction boundary

The PDO implementation supports SQLite: it begins through `PDO::beginTransaction()` and takes the database's write reservation at once, as `BEGIN IMMEDIATE` would, so the audit store and the application's own code on the connection join it. The Doctrine adapter supports SQLite, PostgreSQL, MySQL and MariaDB using its database-specific locking and isolation rules. Both own the outer transaction. Once something on the connection has committed, rolled back or replaced it, the approval store refuses to write anything more in it, so an action that ends the transaction itself gets no outcome recorded. Business state, current authorization data, credentials, proposals and execution records must use the **same application connection**. The [Doctrine guide](../src/doctrine/README.md) documents the supported configurations and ORM boundary.

The initiating user and approving browser user must be the same account in the same tenant. Completion rechecks the original delegation's current permissions; the browser's broader privileges do not replace them. The adapter checks current resource versions before writing and checks the resulting business state before commit.

Failures roll back the protected effect, credential updates, consumed approval and result together. When the action fails after the passkey check, the service retires that ceremony, so trying again needs a fresh passkey assertion. A refused assertion leaves the ceremony as it was until it expires; the bundle's review page still needs a fresh one, because it ends the browser's pairing with a ceremony before completing it. If the commit outcome is uncertain, it checks persisted state before reporting success, failure or uncertainty. A caller should read the existing request's status rather than start a new action blindly.

This transaction does not include remote HTTP or MCP calls, email, payments or nontransactional hooks. The supplied PDO and Doctrine adapters are covered by storage contracts. Another database adapter must preserve those contracts and pass the contention and rollback checks.

## What the passkey proves

The WebAuthn challenge binds a fresh 32-byte nonce to the digest of the frozen proposal, with a versioned domain separator. The evidence includes the nonce so a verifier can recompute that binding.

`web-auth/webauthn-lib` validates the signature, challenge, configured origin, relying party, credential ownership and required user verification. Device verification can use a fingerprint, face, PIN or passcode through WebAuthn. No separate biometric mechanism is needed. Biometric data stays with the authenticator; the application receives the assertion.

The browser review page displays the business proposal. The operating system's passkey prompt verifies access to the credential; it does not independently display or attest all business content. Approval establishes that the enrolled credential approved this proposal. It does not establish who wrote the content or whether a person understood it.

The WebAuthn package registers passkeys without attestation: `WebAuthnVerifier` asks for none and accepts only the `none` attestation format, so no host can require attestation through it. Registration therefore does not establish that a credential lives in particular hardware, and does not prevent a deliberately enrolled software authenticator. User verification also does not establish which biometric or device unlock method was used.

## What must be frozen

The proposal is stored as canonical JSON, not rebuilt from later live values. It includes the actor, target, effect, preconditions, review content, the approval rule and its version, and the approval statement.

The core rejects mutation of the frozen data around adapter callbacks. The adapter must still declare every dependency that matters and verify the actual final effect. For example, if an image affects what is being approved, freeze its content or content digest; a URL whose bytes can change is not enough.

## Protection after storage

With a receipt signer configured, `ApprovalService` signs the proposal, passkey proof and execution report inside the completing transaction. If signing fails, or the application's trusted keys would not accept the signer at the time the execution is recorded, that transaction rolls back. Keep the signing key outside the database. [Verify a receipt](evidence.md) explains the two signatures and walks through a verification.

The demo also records passkey enrollment and revocation in a signed audit log. `AnchoredCredentialRepository` accepts a current credential only if its identity matches a valid signed enrollment, no entry or row names its revocation (a damaged one counts), and every entry recorded since the enrollment is one the audit log accepts: signed by a trusted key over what its row says, inside that key's window, not after the rotation away from that key, and following the one before it. An entry signed with a key that has an end, as a key being retired has, is held to more: nothing before it may be damaged, so no entry before it may have been edited, removed or put out of order, nor be a rotation entry, or another entry of that key's, that the log refuses. The revocation is read from the whole chain, never from the store's lookup. So deleting, damaging, retargeting or re-typing a revocation row, editing the Doctrine store's subject digest, or rewriting the revocation with a retired key does not restore the passkey; only the two edits described below, which a checkpoint shows, can. Inserting a new credential row or replacing its public key in the database does not supply that enrollment proof. Hosts must wire this repository and record enrollment events to get this protection; a plain credential repository alone does not provide it. The wrapper accepts any `RevocableCredentialRepository`, and the log keeps its rows through an `AuditStore`, so a host can use its own storage. A revocation and its signed entry must commit in one transaction: the demo's owner and administrator routes both do, and a failure to sign or store the entry leaves the passkey active.

This fails closed. From the chain alone, an entry the log refuses could be what is left of a revocation, so until the log accepts that entry, it stops every passkey enrolled before it, and a person left with only such passkeys is told to ask the site's administrator (`credential_unvouched`). Editing or retargeting an entry in the database, or removing one that a later entry follows, does this until the rows are put back as they were. Removing the newest entries leaves no later entry to show the cut: only a checkpoint shows it, as described below. An entry refused only because the host's trusted keys do not list its key yet, or give that key a window that misses the entry's time, is accepted once they list the key with a window that covers it. One a retired key signs after the rotation away from it, as a host or worker still on the old configuration can, stays refused whatever window that key is given ([below](#signing-keys-and-rotation)). The owner can instead enroll a new passkey, if the key that signs its enrollment has no end. Since the stopped ones cannot confirm it, the enrollment needs another authorization, such as a one-time link. An administrator's passkeys enrolled before the refused entry stop too, so the host's recovery process needs a way to authorize enrollment that does not rest on them. The bundle leaves enrollment and recovery to the host ([enrollment guide](../src/symfony-bundle/docs/enrollment.md#revocation-and-recovery)); the demo's way is under [Browser and account controls](#browser-and-account-controls).

These signatures make later changes detectable when verification runs. They do not stop someone with database write access from changing or deleting bytes. The default exporter refuses a completed action whose original receipt is missing. It does not replace that receipt with a fresh signature.

The service does not wait for someone to run verification. Each time `ApprovalService` reads a stored request, to report its outcome, return it again for a request key, offer it for approval or change it, it first checks that the stored status and result agree with the execution record. With a receipt signer configured, a completed request must also carry the receipt signed as it committed, and that receipt must verify against the application's trusted keys. A contradiction, a missing receipt, a receipt that names a key the application does not trust, or a signature that fails raises `record_integrity_error`. So does a record edited so far that it cannot be read back at all: a proposal that no longer matches its digest or is no longer a proposal, a result, proof or execution record that is not a JSON object, or a status the application does not know. Present that as an outcome the application cannot vouch for, never as a refusal and never as a sign that nothing happened: the bundle's review page, its status route and its MCP tools answer `integrity_error`. Only the request's owner is told, with what failed; anyone else gets `not_found`, as for a request that does not exist. The exception is a record whose proposal itself no longer reads back. It no longer shows whose it is, so whoever names its id, from any signed-in account or any agent connection allowed to ask for an approval's status, is told `record_integrity_error` and that its proposal fails its check, and nothing about the rest of the record. Request ids are not secret: a review URL carries one, and a public "verified" badge links to one. This read check verifies the application's receipt. It does not repeat the passkey signature check, which the audit page and the offline verifier make with a trusted credential record.

The read check has two limits. Without a receipt signer the service can only check that the stored parts agree, and someone who can edit all of them can keep them consistent. With one, it is strict about history: a request that completed before signing was turned on has no receipt, and one whose receipt was signed by a key missing from the trusted keys cannot be verified, so both read as integrity errors. Turn signing on before the first action runs, and list every retired key when you rotate.

The person's downloaded receipt, and the copy in the agent's result, sit outside the application's database. Checked against the application's published keys, they show a later change to, or deletion of, the stored record. They cover only that person's own requests, and they depend on the person keeping them.

The demo's administrator page at `/admin/audit` rechecks completed actions against their receipts and the passkeys' signed enrollment records. It reads the store directly, so a request that fails the read check stays in its list, marked as an integrity error instead of showing its stored outcome; a status edited to something other than completed does not take the stored execution out of the receipt and passkey checks. A record that cannot be read back at all is listed as a record that cannot be read, with its request id and what failed, to the administrators of the organization its stored proposal names, or to every administrator when it names none. Its evidence route, `/admin/audit/{id}/evidence`, answers `integrity_error`. The page also verifies the audit chain. This checks the original historical records, not whether today's live content still matches an earlier approval.

Recorded times remain application claims, and an old assertion does not independently prove its historical revocation status. Two audit-log edits cannot be detected without an independently retained checkpoint ([below](#signing-keys-and-rotation)): deleting the newest entries, and, by someone holding a retired key's private half, replacing the newest entries with entries signed with that key and backdated into its window, reaching back to the rotation away from it once that is recorded. A passkey whose revocation is among them can approve again until the edit is found. A compromised application signing key can forge application reports or new enrollment records; it cannot recreate a passkey assertion under a separately trusted original user public key. Obtaining and retaining trusted verification keys is therefore part of the host's responsibility.

Checking the audit log takes longer, and more memory, as the log grows. An approval reads the whole log twice, once to prepare the passkey prompt and once to check the passkey's answer, however many passkeys the person has. Each reading checks the Ed25519 signature of every entry since the earliest enrollment of the passkeys it weighs, or of every entry once that enrollment or a later entry is signed with a key that has an end, as after a rotation. One `AuditLog` checks each signature once and remembers up to 50,000 that verified. So a request checks each entry at most once, and a long-running worker that keeps its `AuditLog` checks only entries it has not seen; in a longer log, the entries beyond those 50,000 are checked at each reading. A reading also holds the whole log in memory until it is done: every row, and the entry decoded from each one it checks. Entries come from account events and key rotations, never from approvals: passkeys enrolled and revoked, rotations, and what the host records, which in the demo is enrollment links issued, agent connections revoked and alerts taken down. Rule changes are approved actions and add none. One log serves every tenant, so each tenant's events lengthen it for all of them.

Measured with PHP 8.3 and SQLite on an Apple-silicon laptop, a reading that checks the whole log, as for a person whose passkeys were enrolled at its start or before a rotation, takes about 60 ms with 1,000 entries and 310 ms with 5,000 in a request of its own, and about 14 ms and 75 ms in a worker after its first request.

What a reading holds depends on the entries. At an approval step's peak, a small entry, such as an agent connection revoked, holds about 3.2 KB, and a passkey's enrollment, which carries the passkey's registration, about 4.3 KB; a full check, `AuditLog::verify()`, holds about 3.5 KB and 4.6 KB. A step that checks only the newest entries still holds about 1.6 KB for each small entry in the log and 2.1 KB for each enrollment. Under PHP's default `memory_limit` of 128M, a long enough log makes a check fail with a PHP fatal error, not a refusal: an approval step then stops before anything is approved, with a server error. How soon depends on those entries, on the store and on what else the process holds:

- `verified-human-approval:audit-head` fails at about 35,000 small entries, or 27,000 enrollments, in the demo, and at about 33,000 or 25,000 in the [Doctrine publishing example](../examples/doctrine-publishing/README.md), which runs with debug on as it is set up.
- The demo's audit page, which also lists every entry, fails at about 31,000 or 23,000.
- In a script that loads only the library, a full check fails at about 36,000 or 28,000, and an approval step at about 38,000 or 29,000.

With the limit raised, a full check of 60,000 small entries takes about 3.4 s and 200 MB, and about 1.1 s when the same `AuditLog` checks them again. Raise `memory_limit` for the requests, commands and workers that check the log well before it nears these lengths, and expect time and memory to grow in step with it.

## Signing keys and rotation

Receipts and audit entries are checked against the application's trusted keys: every public key it has signed with, each with the window it signed in. A record names its key. A key the verifier was not given verifies nothing, and a record whose own time falls outside its key's window fails: a receipt's `recordedAt`, which it signs, or an entry's `at`. One current key signs new records. Rotating it adds the new key, closes the old key's window, and appends a `signing_key.rotated` entry, signed with the new key, so the chain records where trust moved. From that entry on, the audit log refuses any entry the old key signs, whatever time it claims. A host or long-running worker still on the old configuration can write entries the log refuses: dated after the old key's window closed, or recorded after the rotation entry. Like any entry the log refuses, each stops every passkey enrolled before it ([above](#protection-after-storage)): one recorded after the rotation entry for good, so their owners must enroll new passkeys; one recorded before it only until the old key's window is moved to cover the time it claims, which also widens the window a stolen copy of the old key can backdate records into. And once the old key has an end, damage anywhere in the chain stops the passkeys it enrolled (below). So check that the chain verifies before you rotate, switch every host and worker to the new key in one deploy, and record the rotation only once they all sign with it. The bundle publishes the keys at `/approval/receipt-keys.json`, and gives the same keys to the approval service for its read check; [Rotate the signing key](evidence.md#rotate-the-signing-key) gives the procedure.

Rotation limits future exposure. It cannot stop someone who stole a key from backdating records into that key's window, because the times a record carries are the application's own claims:

- **Receipts** are not in the chain, so a backdated receipt signed with a stolen key verifies. Only the key's window bounds it.
- **Audit entries** must also fit the chain. Once a rotation is recorded, an entry the old key signs after it is refused, whatever time it claims, and it stops every passkey enrolled before it. Damaging the rotation entry, signing it again with a retired key or hiding it from the store's lookup changes nothing, even while the old key's window is still open: what a key with an end signed after an entry that was edited, removed or put out of order, after a rotation entry the log refuses, or after another entry of its own that the log refuses counts for nothing. So such damage also stops the passkeys a retired key enrolled, wherever in the chain it is. A backdated entry has to replace one from before the rotation, which breaks the chain at the next entry unless every entry from there on is rewritten too. `AuditLog::verify()`, which the audit page runs, reports each refused entry. `AuditLog::find()`, which passkey anchoring uses, counts an entry signed with a key whose window has closed only while a later entry signed with a key in use vouches for it through entries the log accepts.
- **Cutting the chain back** to before the rotation and rewriting it from there is shown only by a checkpoint kept outside the application. `verified-human-approval:audit-head` then also names the old key and asks for the rotation away from it to be recorded.

So keep independent checkpoints of the audit head: its newest sequence and hash, where the application cannot write, on a schedule and after every rotation. `verified-human-approval:audit-head` prints one and checks a kept one; `AuditLog::head()` returns it without the bundle. If a key may have been exposed, follow the [compromise procedure](evidence.md#if-the-signing-key-is-compromised).

## Browser and account controls

The Symfony review flow uses an interactive session, ownership checks, CSRF protection, session-to-ceremony pairing, bounded request bodies, rate limits, escaped output, a restrictive content security policy, frame blocking and no-store responses. Delegated history reads also need an explicit result-read permission through `ActorProvider::assertCanReadApproval()`. Losing write permission need not remove permission to read an earlier result. Each call to a protected tool that may open a proposal spends from the person's budget for agent requests (`agent_requests_per_minute`, 30 a minute by default, shared by all their agent connections); reading an outcome spends nothing.

A token's scopes are checked where they are used: a tool decides with the validated token, and the authorizer rechecks the stored grant when an approval completes. Where the MCP endpoint is an OAuth protected resource, the bundle's `McpScopeChallengeSubscriber` can also refuse a token that lacks one of a tool's scopes before any MCP code runs. It answers HTTP 403 with a challenge naming every scope the operation needs and the protected resource metadata, so a client can ask the person for more and retry. It reads the tool from the parsed request body, never from a header. It finds the endpoint by the MCP bundle's controller, and a container that registers it without one does not build. It grants nothing and replaces no check: the tools and the authorizer still decide, and ownership and permission refusals remain tool results, because they are not requests for a broader token. The demo registers it; the [guide](../src/symfony-bundle/docs/index.md#scope-challenges-over-http) says when to.

The demo keeps bearer-authenticated MCP access separate from human sessions, enrollment and administration. Its account controls illustrate responsibilities a production host must implement:

- A first approval passkey requires a one-time enrollment link and the owner's signed-in session. Setup issues initial links; an administrator needs fresh passkey confirmation to issue another.
- Adding another passkey requires the owner's signed-in session and either a fresh confirmation with one of their existing passkeys or a new one-time link from an administrator. A password alone cannot enroll an approval credential.
- Passkey and agent-connection revocations are recorded and checked for subsequent use.
- A person whose passkeys have all stopped (see [Protection after storage](#protection-after-storage)) adds a new one with a one-time link from an administrator. If the administrator's own passkeys stopped too, they cannot confirm to issue one, and the demo has no other way to issue a link: only a link issued earlier that is still unused and unexpired (setup's last seven days, an administrator's one day), or a fresh demo (`php demo/bin/setup.php --reset`, which replaces every account, passkey, connection and record, and the signing key), lets them add a passkey again.
- Changing who must approve is itself a passkey-approved action. Its approval rule is fixed in code, so an administrator cannot switch off approval of rule changes through that rule editor.

The phone code is 32 random bytes and opens one pending request's review page, for the person who owns it, once, within two minutes. It is a pre-authenticated link: whoever redeems it first gets that one review. A Continue step keeps a link previewer from spending it, and redemption is locked. The session it opens lasts ten minutes, reaches no other page, and can approve with the person's passkey, but cannot cancel or download the receipt; a browser that is also signed in as the same person keeps both, since cancelling and the download check the signed-in session. Both times are measured by the application's clock. The session's approval attempts count against a budget of their own, so a phone code cannot use up the signed-in person's. The tool that creates codes checks the same read permission as the status tool, has its own per-person budget, and makes a code only when the application's origin is HTTPS. Its app-only visibility is a host convention, not authorization. The codes are kept in their own cache pool, `verified_human_approval.handoff_cache`. A site that does not want the phone code sets `phone_handoff: false`: the card then offers no code, the tool is not defined, and a code link answers 410.

The demo's consent page asks the person about the exact authorization request the server validated, and Allow approves that one request, once and within ten minutes. Don't allow sends the person back to the client with `access_denied`, the request's `state` and the issuer (`iss`), but only when a trusted client ID metadata document names the client or its return address is on this computer. A client that registered itself and returns to another computer chose that address itself, so refusing it ends on the demo's own page, and its scope errors are answered without a redirect too, as RFC 9700, section 4.11.2 asks. Dynamic client registration is on by default only for a demo on this computer, and off on the public demo. Access tokens name the demo's `/mcp` as their `aud` and `resource`, and `/mcp` answers 401 to a token that names it in neither.

The demo accepts client ID metadata documents only over HTTPS from `claude.ai`, `chatgpt.com`, `vscode.dev`, `cursor.com` and names under them. It fetches them through `NoPrivateNetworkHttpClient`, with no redirects and limits of 64 KiB and 10 seconds, so a client cannot make it reach a private network. Its OAuth integration (League's OAuth2 server bundle and the MCP OAuth bundle, with the demo's own storage and consent page) and its personal tokens are reference code. A production host connects its own identity provider and account recovery.

## Deployment responsibilities

Share rate-limit and lock storage where a deployment runs on multiple hosts. Keep runtime settings, signing keys and database files outside the public document root. Keep assertions, tokens and complete approval content out of routine request logs.

This is a tested initial implementation, not an independent security audit. [Verification status](verification.md) lists the automated checks, the recorded runs with real clients and devices, and what is not proven. The [Symfony guide](../src/symfony-bundle/docs/index.md) covers integration and [what to do before deployment](../src/symfony-bundle/docs/index.md#before-deployment).

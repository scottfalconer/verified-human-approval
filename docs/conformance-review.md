# MCP conformance

How the packages and the demo use the Model Context Protocol and its MCP Apps extension: what they implement, where they depart from the specification on purpose and why, and what limits clients meet. This page describes the code in this repository. It is not a certification. [Verification status](verification.md) says which clients have been tried, and when.

## Versions

- MCP specification [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28). Clients on the 2025-11-25 revision, which starts with `initialize` and keeps a session, are served too.
- MCP Apps [2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx), the extension `io.modelcontextprotocol/ui`.
- The PHP MCP SDK, `mcp/sdk` 0.9.0, and the Symfony MCP Bundle, `symfony/mcp-bundle` 1.0.0-BETA1: the locked versions. The packages require `mcp/sdk` `^0.9` and `symfony/mcp-bundle` `^1.0`.

## Tools and results

- **A protected action is an ordinary tool.** The demo's `publish_alert` is a plain `#[McpTool]` that calls `ApprovalFlow::respond()`. It declares a `title`, described parameters, annotations that match what it does, and `ApprovalFlow::OUTPUT_SCHEMA` as its `outputSchema`. The SDK checks the arguments against the tool's input schema before the tool runs, and a successful result's `structuredContent` against its output schema as it is sent.
- **Structured results come as text too.** An approval result, from a protected tool or the status tool, and an error result from `ApprovalFlow::errorResult()` carry `structuredContent` and the same JSON as text, as the [tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) asks for backwards compatibility. A host without MCP Apps gets the review URL in that text. The phone-code tool's text says what its code is for; its structured content is for the card.
- **Pending is a result, not an error.** A tool that needs approval returns `status: pending` and the review URL. A protected tool's refusal is a tool execution error (`isError: true`) with `status: rejected`, a `reason` and a `message`, so the model can read why. A stored record that cannot be trusted is refused with `record_integrity_error`: one that no longer reads back, such as a proposal that fails its digest, a result that is not JSON or a status that does not exist; one whose status or result contradicts its execution record; and, with a receipt signer, a completed one whose commit receipt is missing or does not verify against the trusted keys. That is reported as `status: integrity_error`, never as `rejected`, because it does not say whether the action ran. `ApprovalFlow::errorResult()` builds both.
- **A request id is a handle, not a capability.** Request ids are `apr_` and 128 random bits. On every call, the status tool, the phone-code tool and the review pages check that the request belongs to the caller's account and tenant, as the [security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) ask of state handles. Anyone else gets the answer a request that does not exist gets (from the status tool, a plain text error), even when the record is damaged. Only a record whose proposal no longer reads back shows no owner, so whoever names it is told that its proposal fails its integrity check, and nothing more.
- **A retry does not run an action twice.** A repeated call from the same connection with the same arguments returns the same pending request, and makes a new one only after that request has finished. A tool may also take an optional request key. Its description, `ApprovalFlow::REQUEST_KEY_DESCRIPTION`, tells a model to leave the key out, because a key used before returns that earlier request and its outcome. When the request a key names finished before the call, the result says so: its `message` says this is the earlier request's recorded outcome and that nothing ran now, `approval.earlier` is `true`, and the card heads it "Earlier request on …" and, for one that completed, says "Completed earlier, on …".
- **The tool list comes from the SDK's registry.** `tools/list` includes the tools linked to the card. Listing tools needs no scope.
- **Inputs, access and outputs.** The tools specification says servers must validate tool inputs, control access, rate limit tool invocations and sanitize outputs. The SDK validates arguments against the input schema, the action adapter validates what it reads, and the core refuses an input over 256 KiB, and, as `invalid_input`, one holding a value that is not exact JSON data, such as a decimal. A protected tool's own arguments may hold decimals, which `ApprovalFlow` accepts; the action's input takes them as strings. The tool checks the token's scopes, and the application's authorizer checks current permissions when the request is made, before the action runs and again before it commits. Results are JSON the application builds from its stored record, and the card writes only text.
- **Calls that ask for an action are rate limited.** `ApprovalFlow::respond()` spends one from the person's budget on every call to a protected tool that may open a proposal, before anything is prepared. Once it is spent, the call is refused with `status: rejected` and the reason `rate_limited`. In Symfony the budget is `agent_requests_per_minute`, 30 by default, kept per person across their agent connections by the framework rate limiter `verified_human_approval_agent_requests`, and an application can define its own `ProposalBudget` in its place. Phone codes from `approval_handoff` and approval attempts on the review page each have a per-person budget of `attempts_per_minute`, kept by the framework rate limiter `verified_human_approval` unless the `rate_limiter` setting names another. A phone session's attempts have a budget of their own, so whoever holds a phone code cannot use up the signed-in person's.

Not met:

- **Calls that only read are not rate limited.** `approval_status`, the retry that answers a URL prompt and the demo's `read_alert` read what is stored and spend no budget, so nothing limits how often an agent reads. For those calls this falls short of the tools specification's "Rate limit tool invocations".

## Elicitation

- **The prompt uses multi round-trip requests.** For a pending approval, `ApprovalFlow::respond()` can return an `InputRequiredResult` whose `inputRequests` hold one URL-mode `elicitation/create` and whose `requestState` lets the retry continue, as the [multi round-trip pattern](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) describes. It never calls `ClientGateway::elicitUrl()`, which holds the HTTP request open on a handshake-era connection.
- **When it is sent.** Only when all of these hold: `url_elicitation.enabled` is true; the request uses the 2026-07-28 revision; the client declared `elicitation.url` on that request; and the client's `clientInfo.name` is in `url_elicitation.clients`, or that list holds `'*'`. It is off by default. Listing clients turns it on, and `enabled: false` turns it off and keeps the list; the [Symfony guide](../src/symfony-bundle/docs/index.md#4-register-the-mcp-tools-and-card) shows `'*'`, which leaves the decision to the capability each client declares. A 2025-11-25 client never gets it, because the SDK's `InputRequiredShim` would turn it into a blocking `elicitation/create` that holds the call open while the person approves. Every other client gets the plain result with the review URL.
- **The request state.** The SDK signs it with HMAC-SHA256, using the server's `request_state.key` of at least 32 bytes, with an expiry inside the signed body. It does not encrypt it. A server without that key refuses a call the prompt is for before it spends the budget or prepares anything, so no proposal is left that nobody was shown. The state carries a format name, the request id and a binding: SHA-256 over the caller (user, tenant and agent connection), the tool name and the arguments. A retry with another caller or other arguments fails with `continuation_mismatch`. These are the three things the pattern recommends against replay: the principal, an expiry and the originating request. A retry only reads the stored request, so replaying the state within its lifetime changes nothing.
- **The URL.** It is the application's own review page, `/approval/{id}`, on its configured origin, which must be HTTPS, or `http://localhost` in development. It carries no personal data and no credential. The page acts only for the person whose request it is, in the same tenant, known by their own session on the site or by a phone session scoped to this request (below), and refuses anyone else. This meets the [elicitation specification](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)'s rules that the URL is not pre-authenticated and that the server checks who opens it.
- **The answer approves nothing.** `accept` only means the person agreed to open the page. The application acts after its own passkey check, and the retry reports the outcome it recorded. The prompt does not authorize the client: its token and scopes stay as they were, and what the person approves is one stored action. So the server does not rely on URL-mode elicitation to authorize users, which the specification forbids; [MCP presentation](../src/mcp/README.md#the-url-mode-elicitation-and-its-retry) quotes the rule.
- **Decline, cancel or no answer.** The request stays open, and the person can still approve or cancel it on the site. A retry without an answer reads the stored request instead of asking again, because the answer never decides the outcome.

Deviation:

- **The prompt is sent by client name.** The specification says implementations SHOULD NOT use `clientInfo` to change their behavior. Some clients declare URL mode and then decline, drop or fail on the request, and on 2026-07-28 the first answer carries no tool result, so such a client would leave the person without the link. The list is an interoperability allowlist, not a security decision: a client that gives a false name only receives a prompt it declared it can handle, and the card and the link are always there. `'*'` turns it into capability-only gating. The demo lists `claude-code`.

### The phone code is a pre-authenticated URL

The card's **Approve on your phone** button calls the `approval_handoff` tool, whose result carries a one-time link and the QR code of that link, which the card draws. Whoever redeems that link first gets a browser session scoped to one request, so it is a pre-authenticated URL. The elicitation specification says a server requesting elicitation must not provide a URL that is pre-authenticated to a protected resource. The review URL the prompt sends obeys that rule. This link travels in a tool result, not in an elicitation, so the rule does not bind it, but it is stated here.

- The code is 32 random bytes and opens only its pending request's review page, for the person who owns it. It works once and expires two minutes after it is issued; a Continue step keeps a link previewer from spending it. The session it opens lasts ten minutes. Both times are measured by the application's clock.
- The scoped session can read that one review page and start the passkey step. It cannot cancel the request, download the receipt or reach any other page, and approving still needs the owner's passkey. Its approval attempts have a budget of their own.
- The tool checks the same read permission as `approval_status`, has its own per-person budget, and makes a code only when the application's origin is HTTPS.
- The bundle's `phone_handoff` is on by default. While it is on, a container in which an MCP server serves the card without the tool does not build, so the card is never told to call a tool its server lacks. A site that does not want the phone code sets `phone_handoff: false`: the card then offers no code, the tool is not defined, and a code link answers 410.

## MCP Apps

- **The card.** `ApprovalCard::resource($origin, $statusTool, $handoffTool)` serves `ui://verified-human-approval/approval-card.html` as `text/html;profile=mcp-app`, with `_meta.ui.prefersBorder: true`. It writes into the card the review pages' origin and the tools the card may call, so the card opens pages on that origin only and calls only those tools, whatever a result names, and does not show a result that links to another site. In Symfony, `ApprovalCardApp` registers it through the MCP bundle's `#[AsMcpApp]`, which also declares the extension, and serves it written for the bundle's `public_origin` and tools. A protected tool links to it with `_meta.ui.resourceUri` (`ApprovalCard::TOOL_META`). The card declares no `csp`, so the host's restrictive default applies; it loads nothing from the network.
- **Messages.** The card sends `ui/initialize` (protocol version 2026-01-26), declaring in `appCapabilities.availableDisplayModes` the one display mode it supports, `inline`; then `ui/notifications/initialized`; and `ui/notifications/size-changed` whenever its content changes and, where the browser has a `ResizeObserver`, whenever the host's fonts or the frame's width reflow it. It sends `tools/call`, to the status tool and to the phone-code tool, only if the host declared `serverTools`, and `ui/open-link`, for the review page, only if the host declared `openLinks`. It handles the `tool-input`, `tool-result`, `tool-cancelled` and `host-context-changed` notifications, answers `ping` and `ui/resource-teardown`, and refuses any other request with `-32601`. It accepts messages from its parent window only, and posts nothing secret.
- **What the card says.** It shows an outcome only as the site recorded it. A refusal, also one that names no request, reads "The site refused this request. Nothing changed."; an invalidated or denied request is told in the review page's own words, without guessing at the cause; a status the card does not know is shown as it is; and an `integrity_error` is shown as an outcome the card cannot confirm, never as "nothing changed". Its other lines say what the card itself knows, such as that it is waiting for the request, cannot check the outcome in this host, or has stopped checking. None of them claims an outcome.
- **No passkey in the card.** The card never runs WebAuthn. It runs on the host's sandbox origin. The verifier accepts a ceremony only on the application's exact origin and refuses one embedded in a page of another origin, and the bundle's review pages cannot be framed. So no assertion obtained in the card could pass.
- **The phone-code tool is app-only.** `approval_handoff` is a plain `#[McpTool]` whose `_meta.ui` names the card with `visibility: ["app"]`, so it can declare annotations and an output schema, which the MCP bundle's `#[AsMcpAppTool]` cannot. Visibility is a rule for hosts, not a server boundary: the tool checks the caller's read permission and its budget itself.

Deviation:

- **UI-linked tools are listed to every client.** The extension recommends checking the client's capabilities before registering UI-enabled tools. MCP 2026-07-28 carries [client capabilities](https://modelcontextprotocol.io/specification/2026-07-28/basic) on each request, including `tools/list`. The PHP SDK's list handler returns the registered tools with their `_meta.ui` regardless of the extensions the client declares. A host without MCP Apps ignores the UI metadata and can use the review URL from the tool result.

Interoperability:

- **The way back.** Only when the host names itself Claude, by `hostInfo.name` in its answer to `ui/initialize` or by `hostContext.userAgent`, does the card open the review page with `#return=claude-desktop`, `#return=claude-mobile` or `#return=claude-web`, so that the completed page offers Claude's own way back. Any other host gets `#return=agent`, and the page keeps its own line, which names the agent by the bundle's `agent_name`. A host's name is not verified, so this decides nothing about security: a host that names itself wrongly only changes which button the completed page offers.
- **Theme colors.** On 18 November 2026, in the Claude iOS app, an earlier version of the card showed dark text on a dark surface: it set `data-theme` but no `color-scheme`, and its body was transparent. The card sets `color-scheme`, paints its own surface, and uses the host's colors only as a pair that is readable in the host's theme. [`card_smoke.py`](../tests/card_smoke.py), which CI does not run, checks the colors in Chromium under dark, light and mismatched hosts, but no run of those checks is recorded (see [verification status](verification.md#browser-checks-outside-ci)). These colors have not been checked in the iOS app.

## Authorization

The packages contain no authorization server:

- **The host authenticates.** The host's Symfony firewall validates the bearer token and sets the SDK's `AccessToken` request attribute, so tools read its scopes with `RequestContext::getAccessToken()`. The host's actor provider maps the token to the person and their agent connection, and the host's authorizer rechecks that connection's current grant when an approval completes.
- **Scope challenges over HTTP.** `McpScopeChallengeSubscriber`, which an application opts into, applies the SDK's `ScopePolicy` before any MCP code runs. A container that holds the subscriber but not the MCP bundle's `McpController` does not build, so an application with no MCP server over HTTP, or a release of the MCP bundle that serves its endpoint with another controller, fails loudly instead of leaving every request unchallenged. A token that lacks a scope the operation needs gets HTTP 403 with `WWW-Authenticate: Bearer error="insufficient_scope"`, every scope the operation needs in one challenge, the `resource_metadata` URL and a description, plus a JSON-RPC error naming the scopes. A scope the policy says another implies counts. A request that needs a scope and carries no validated token gets 401, and a body too large to inspect gets 413. The tool is read from the parsed body, never from a header. Ownership and permission refusals stay tool results, since a broader token would not change them. The subscriber exists because `symfony/mcp-bundle` 1.0 builds the HTTP transport itself and takes no PSR-15 middleware from the application, so the SDK's `AuthorizationMiddleware` cannot be added ([symfony/ai#2883](https://github.com/symfony/ai/issues/2883)).

The demo's OAuth is reference application code, not part of a package. [demo/authentication.md](../demo/authentication.md) says which component owns what.

- **Maintained providers.** `league/oauth2-server-bundle` 1.2.3, on `league/oauth2-server` 9.4.1, issues and validates the tokens. `omouren/mcp-oauth-bundle` 1.2 adds the MCP parts: protected resource metadata (RFC 9728), authorization server metadata (RFC 8414), client ID metadata documents, dynamic client registration (RFC 7591) and the `iss` response parameter (RFC 9207).
- **Discovery.** The demo builds its metadata from its configured origin, never from request headers. A 401 from `/mcp` names the protected resource metadata in `WWW-Authenticate`.
- **Grants.** Only the authorization code and refresh token grants are enabled. Public clients must use PKCE with S256, the only method the metadata lists, and plaintext client secrets are off. A code works once and a refresh token rotates, both under the application's database write lock (`AtomicTokenController`).
- **The resource and the token's audience.** The only resource is the application's `/mcp`. `ResourceTargetGuard` refuses an explicit `resource` that names anything else, and treats an omitted one, or the bare origin, as `/mcp`. Access tokens are signed JWTs whose `aud` and `resource` claims both name that endpoint. On every request to `/mcp`, the MCP OAuth bundle answers 401 to an access token that names neither, which is how the server checks that a token was issued for it, as the [authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) requires. The firewall takes the token's client from the record this server kept when it issued the token, not from the token's claims.
- **Consent.** Every authorization waits for the person on the consent page, which shows only what the server validated for the request waiting in the person's session: the client's registered name; the host of the client ID metadata document that named it, or that the name is not verified when the client registered itself; the host its code returns to, with a warning when that is this computer; and the scopes its token will carry. Nothing in the page's link changes what it shows. Allow approves that one request, for the same person, client, redirect URI, scopes, resource, state and PKCE challenge, once and within ten minutes; any other authorization request is asked about again. Don't allow refuses that one request. The page cannot be framed (`frame-ancestors 'none'`), and its form carries a CSRF token.
- **Refusals and scope errors.** A request for a scope the client was not registered with, or for one this server does not offer, is answered with `invalid_scope` and never shown to the person. That error, and a refusal with Don't allow (`access_denied`), go back to the client only at a return address the server trusts, as RFC 9700, section 4.11.2 asks: one given by the client ID metadata document that named the client, or one on this computer. When the server sends the person there, the redirect carries the error and the request's `state` (RFC 6749, section 4.1.2.1), and the provider adds `iss` (RFC 9207). The address of a client that registered itself and returns to another computer is not trusted, whether the request names it or leaves it out. For such a client, Don't allow ends on a page of the demo's own, and `invalid_scope` is answered as a JSON error. `UnknownScopeGuard` gives that JSON error for a scope this server does not offer, before League would redirect it. It also gives it when a client that registered itself names no redirect URI, even if the client's only redirect URI is on this computer, because the guard does not look that URI up.
- **Redirect URIs.** A redirect URI must be one registered for the client, matched exactly, apart from the port of `http://127.0.0.1` or `http://[::1]`, which RFC 8252 lets vary. It is taken only on https, or on http back to this computer, as the authorization specification's security considerations require of every redirect URI, and only in a plain form that PHP and browsers read with the same host: no backslash, space, user name, fragment or character beyond ASCII. Registration checks this, and so does every authorization before the person is asked, without a redirect, so the host the consent page names is the one that receives the code. An application's own link scheme, such as `cursor://`, is refused, because the page could not say where it sends the code.
- **Client ID metadata documents** are how a client such as claude.ai identifies itself. The demo accepts a document only over HTTPS from `claude.ai`, `chatgpt.com`, `vscode.dev` or `cursor.com`, the hosts the MCP OAuth bundle trusts by default and ChatGPT's, or from a subdomain of one of them. It fetches the document with Symfony's `NoPrivateNetworkHttpClient`, follows no redirect, stops at 64 KiB or 10 seconds, and caches the result.
- **Personal tokens.** The demo also accepts the personal tokens that its setup prints, for local clients such as `mcp-remote` and the PHP examples. The application issues them and stores only their SHA-256 hash; they are not OAuth tokens.

Deviations:

- **A demo on `localhost` or `127.0.0.1` keeps dynamic client registration.** The 2026-07-28 revision deprecates registration in favor of client ID metadata documents, and keeps it for backwards compatibility. Registration is a setting of each runtime. A demo set up for `localhost` or `127.0.0.1`, such as `http://localhost:8080`, offers it at `/oauth/register`, within a budget for each IP address, for clients without a metadata document, such as its OAuth smoke test. At any other address, the public demo's included, it is off unless the runtime turns it on: the metadata names no registration endpoint, `/oauth/register` answers 404, and a client connects over OAuth only with a client ID metadata document from one of the hosts above. `VERIFIED_HUMAN_APPROVAL_DYNAMIC_CLIENT_REGISTRATION=0` or `=1` for `php demo/bin/setup.php` turns it off or on.
- **`scopes_supported` lists all three scopes.** The specification intends it as the minimal set for basic functionality. Issuing an alert needs all three (`alert.read`, `alert.publish` and `approval.read`), so here the minimal set is the full set.
- **A client that registered itself and returns to another computer is not told of a refusal or a scope error.** RFC 6749, section 4.1.2.1 has the server send both to the client's redirect URI. RFC 9700, section 4.11.2 asks it to redirect on its own only to an address it trusts, and anyone can register a client that returns to a site of their own, so the demo does not send the person there. A client that registered itself and names no redirect URI is not told of a scope this server does not offer either, even when its only redirect URI is on this computer: the request gets `invalid_scope` as a JSON error on the site instead of a redirect. Registration is off on the public demo, so there every OAuth client is named by a client ID metadata document.

## Security considerations

- **Sessions on the 2025-11-25 revision are not bound to the bearer.** That revision's [security guidance](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices#session-hijacking) says servers SHOULD bind session ids to user-specific information. It also says they MUST verify every inbound request and MUST NOT use sessions for authentication, and those hold: the `/mcp` firewall is stateless, every request authenticates its own token, and every tool checks that the person owns what it reads. The session keeps protocol state, such as the negotiated capabilities and the client's details, and a session id without a valid token reaches nothing.
- **DNS rebinding.** The SDK's protection stays on. The demo allows only its own host (`http.allowed_hosts`), and a request's `Origin`, if it sends one, must be the server's own.
- **No token passthrough.** The tools call no other service with the client's token. The demo accepts only the access tokens that its League authorization server issued, and the personal tokens it issued itself.
- **Request state is attacker-controlled input.** It is signed, bound to the caller, the tool and the arguments, and only ever read on a retry, as described under [Elicitation](#elicitation).
- **Fetching client metadata** cannot reach private networks, as described under [Authorization](#authorization).
- **The review pages** have their own protections: see [browser and account controls](security-model.md#browser-and-account-controls) in the security model.

## Interoperability limits

- **Clients tried.** Claude Desktop, claude.ai, the Claude iOS app and Claude Code; [verification status](verification.md#real-clients-and-devices) gives the dates and results. No other vendor's host or model has been tried.
- **The URL prompt** reaches only the clients an application lists; the demo lists `claude-code`. A client on the 2025-11-25 revision never gets it, and uses the card and the link.
- **Server instructions** may not reach the model: claude.ai did not pass them on in the run of 8 November 2026. The demo's tool descriptions repeat the essentials: where the alert id comes from, that a pending alert is not live, and to call `approval_status`.
- **Hosts without MCP Apps** show no card, and do not know the `app` visibility, so they can list `approval_handoff` to the model. The review URL is in the text of every approval result.
- **Beta dependencies.** `symfony/mcp-bundle` 1.0 is a beta. The demo's root `composer.json` installs it as `1.0.0-BETA1 as 0.13.99`, because `omouren/mcp-oauth-bundle` 1.2 declares `^0.13`; the packages do not carry that alias. See [reference-only dependency compatibility](../demo/authentication.md#reference-only-dependency-compatibility).
- **Upstream.** Two changes upstream would remove workarounds here: a public `RequestContext::getClientInfo()` in the SDK, and `annotations` and `outputSchema` on the MCP bundle's `#[AsMcpAppTool]`. Without the first, `UrlPrompt` reads the request's metadata from the SDK's session; if that changes, it finds no client name and sends no prompt, and the card and the link still work. Without the second, the phone-code tool is a plain `#[McpTool]`. A third is filed as [symfony/ai#2883](https://github.com/symfony/ai/issues/2883): PSR-15 middleware for the MCP bundle's transport, so that the SDK's `AuthorizationMiddleware` could replace the scope-challenge subscriber.
